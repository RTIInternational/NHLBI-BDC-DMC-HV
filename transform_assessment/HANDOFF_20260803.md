## What is actually wrong — three distinct problems

### 1. HCHS/SOL column blank — FIXED (uncommitted)

`config/s4_layout.yaml` listed `HCHS/SOL` as a display column but had **no
`cohort_keys:` block**. `spec_phv_report.py:527` does:

```python
key_for = lambda disp: layout.get("cohort_keys", {}).get(disp, disp)
```

```yaml
  HCHS/SOL: HCHS
```

- disease/status rows (Diabetes, Hypertension, Angina, Asthma, Obesity, the six

- demographics (Sex, Race, Ethnicity, Death, Cause of death)

**Mechanism, traced end to end.** `spec_phv_report.py` extracts PHVs only from
measurement value slots:

```python
_VALUE_SLOTS = ("value_decimal", "value_integer", "value_coded",
                "value_concept", "value_enum")          # line 82
```

`_value_source_phvs` (line 154) reads only those; `_measurement_observations`
(line 196) is measurement-shaped by name and design. A `DrugExposure` spec
carries its concept in `drug_concept`, a `Condition` in `condition_concept`, a
`Demography` in sex/race/ethnicity slots. None are in `_VALUE_SLOTS`, so
`_value_source_phvs` returns `{}`, `by_type` stays empty, `concepts` is empty,
and the file contributes nothing. It never reaches `_resolve_label`, which is
why the filename-stem fallback that *would* have resolved `tak_statin` never
fires.

## The question that blocks both #2 and #3

**What does "Number of relevant raw variables (phv)" actually count?**

The S4 header says "Number of relevant raw variables (phv) and data points
(excluding missing values)". The generator interprets phv as *distinct
value-source PHVs*. The published sheet clearly does not, at least not only
that.

Attempts to reverse-engineer the rule from the published sheet **failed** — this
was tested, do not repeat it without new information:

| spec | published phv | blocks | `drug_concept` phv | `associated_participant` phv | all phv in file |
|---|---|---|---|---|---|
| ARIC `tak_statin` | 11 | 10 | 10 | 6 | 16 |
| CHS `tak_statin` | 1 | 1 | 1 | 1 | 2 |
| JHS `tak_statin` | 6 | 3 | 3 | 3 | 6 |
| MESA `tak_statin` | 3 | 5 | 5 | 3 | 12 |
| CARDIA `tak_insulin` | 1 | 1 | 1 | 1 | 2 |

No single rule fits: `drug_concept` count matches CHS and CARDIA, undercounts
ARIC and JHS, and *overcounts* MESA. Combined with only 3/148 measurement rows
reproducing, the conclusion is that **the published S4 was produced by a
different pipeline** (old `harmonized_vars.tsv` + var_report XML), not from
today's transform specs. Matching it exactly is not a reachable target.

**This is a curator question, not a coding decision.** Ask it before writing the
non-measurement extractor, because the answer determines what that extractor
counts.

**Siggie has already ruled out one option: NOT "every phv the spec touches."**
Participant and visit key PHVs (`associated_participant`, `associated_visit`)
must not be counted. They are join keys, not variables, and counting them would
inflate every row.

## Open question: when did the `observation_type` requirement appear, and why?

**Siggie's question, and it is the right one to ask before writing any fix.**
Keying variable identity on `observation_type` is what makes 282 non-measurement
spec files invisible (problem #2). It is worth knowing whether that was a
deliberate design decision with a rationale, or something that crept in while
the label source was being migrated — because the same change probably
introduced other bugs nobody has looked for yet.

**Not investigated this session** (the session ran too long). What is known:

- `git log --all -S "observation_type" -- transform_assessment/ hv_dataqc/`
  returns 12 commits. The relevant cluster is `e960fc33` (migrate the label
  source from `harmonized_vars.tsv` to Table S1), `afe880d5`, `6ae9b80a`, all
  squashed into `93ac3910` on the current branch.
- The abandoned branch `feature/S5-report-20260603` still has the **granular,
  unsquashed history** — that is where to look. `93ac3910` is a squash and shows
  nothing about how the design evolved.
- `spec_phv_report.py` does not exist before `93ac3910` on this branch, so there
  is no in-branch diff to read; find its first appearance with
  `git log --all --diff-filter=A -- "*spec_phv_report.py"`.

**What to look for.** The old `harmonized_vars.tsv` keyed on `var_name` /
`var_label` and carried a `DOMAIN` column (MEASUREMENT / MEDICATION / DIAGNOSIS
/ CONDITION / DEMOGRAPHICS / PROCEDURE / DIET). Table S1 replaced it with a
`BDCHM Element` column, which carries the same information in a different
shape. The suspicion worth testing: the migration switched the join from
`var_name` to `observation_type` because that was cleaner for measurements, and
the non-measurement domains were simply not considered — `_resolve_label`'s
docstring argues for the concept-code join purely in terms of measurement
benefits (cross-vocabulary synonym collapsing for HDL/LDL/triglycerides) and
never mentions the other classes.

If that is what happened, then `BDCHM Element` + `var_name` is the join the
extractor should use for non-measurement classes, and the fix is closer to
"restore what `harmonized_vars.tsv` did" than to "invent a new rule."

**Also worth auditing while in there:** whatever else that migration changed
without a test. The `cohort_keys` omission (problem #1) was exactly this shape —
code and unit test both correct, config silently missing an entry, no test
covering the real config file. Look for other config-vs-code gaps of that kind.
