### 3. Non-measurement PHV extraction rules — settled with Siggie

Siggie's reading of the four representative specs, confirmed against the files:

| class | rule | note |
|---|---|---|
| MeasurementObservation | `class_derivations → slot_derivations → value_decimal → populated_from` | the working case |
| Condition (`ARIC-ingest/diabetes.yaml`) | `condition_status → populated_from` | `condition_concept` is a constant, contributes nothing; age-expression PHVs do not count |
| Demography (`ARIC-ingest/demography.yaml`) | `sex` / `race` / `ethnicity` → `populated_from` | one file → three S4 rows |
| DrugExposure (`ARIC-ingest/tak_statin.yaml`) | `drug_concept → expr` | one PHV per `case()` line **in ARIC** — not verified across all 95 DrugExposure specs, sweep before hardcoding |

Ruled out everywhere: `associated_participant`, `associated_visit` (join keys,
not variables). Also ignore `identity`, `id`, `species` on Person.

Ages are out of scope — there is no age variable in S4, so
`age_at_condition_start` / `age_at_death` need no decision.

### 4. Demography and Person both need slot-level mapping

Verified against the BDCHM schema and all 23 live spec files.

**Demography** schema attributes are exactly `sex`, `race`, `ethnicity`, and all
23 specs use those names with no variants. JHS lacks `ethnicity` — real data,
not a naming problem.

**Person** carries the death variables, with slot names that do not match the S4
labels:

| S4 row | Person slot | files |
|---|---|---|
| Death | `vital_status` | 6 |
| Cause of death | `cause_of_death` | 7 |

So one config map covers both classes:

```yaml
slot_variables:
  Demography: {sex: Sex, race: Race, ethnicity: Ethnicity}
  Person:     {vital_status: Death, cause_of_death: Cause of death}
```

That is 5 of the 48 non-measurement rows. The other 43 (Condition, DrugExposure,
Procedure) stay per-file on filename stem. **The extractor dispatches on `BDCHM
Element`:** these two classes use the slot map, the rest use the stem lookup.

**Open issue — CARDIA `cause_of_death` appears twice.** CARDIA has both
`cause_of_death.yaml` and `person.yaml`, and both define a `cause_of_death` slot
on `Person`. Every other cohort has it only in `person.yaml`. The extractor must
not assume one file per (cohort, class) — it needs to union PHVs across files, or
it will double-count or pick arbitrarily. Asked of the group 2026-08-04; awaiting
an answer on whether to union, treat one as authoritative, or clean up the
duplication.

LTRC and SPIROMICS `person.yaml` contain only `identity`/`species` — nothing
countable. This is independent of their absence from S4; see the correction
below.

## The open investigation: generation and count bugs

**This is the next session's whole job.** Highest priority, and Siggie's position
has hardened since the last handoff:

> Forget what I said earlier about trusting earlier versions to be plausible. At
> this point I don't trust any of it and am wondering if counts got pasted into
> the wrong lines or what.

That supersedes the prior handoff's "the published sheet is not an oracle, but it
is plausible." **Treat no version of the sheet as ground truth.** The working
hypothesis is now that some published numbers may be misaligned with their
variable labels, not merely computed differently.

### Why misalignment is plausible

The sheet was not always machine-generated. Siggie's account: xlsx generation is
recent; **before that, a TSV of just the counts was pasted into cell B5** — so
the counts were positionally aligned to the label column by hand, with no key
joining them. Any row insertion, deletion, or reordering between the generator's
row order and the sheet's row order silently shifts every count below it.

Siggie has a vague memory of the first line (`8-epi-PGF2a in urine`) getting
repeated, possibly a paste mistake, and does not know whether it shows up in the
saved sheets.

**There is a lead on exactly that.** In `s4-gsheet-2026-06-25-new-s4-data.xlsx`,
the TOTALS column (cols 20/21) begins:

```
row5: 2 / 3096
row6: 2 / 3096      <- same values repeated
row7: 19740
```

whereas the two earlier sheets have `2/3096` then `7/19740` in those rows — i.e.
the later sheet looks like it has a duplicated first data row, pushing everything
down by one. **This was spotted and not yet confirmed against the label column.**
Confirming or killing it is the first concrete task, because if row alignment is
off in the published sheet, every per-row comparison done so far is meaningless.

### Method for the deep dive

Siggie's framing: *"I doubt we'll be able to solve the problem without relating
count changes to script changes."* So the shape of the work is:

1. **Confirm or kill the duplicated-row lead** in the 2026-06-25 sheet. Check the
   label column against the count columns, and check whether label→count pairing
   is consistent with the 2026-03-23 sheet. Rows should match exactly across
   versions; if they don't, that alone explains arbitrary amounts of the
   discrepancy.
2. **Ask Siggie to add the recent exports** (2026-07-28 and yesterday's) to
   `old_files/xslx/`. He offered; they are not there yet. They bracket the most
   recent changes and are likely the most diagnostic.
3. **Build a version × script-change timeline.** For each sheet transition, find
   what changed in the generator between those dates. The 2025-08-05 →
   2025-12-23 inflation is the biggest unexplained event; start there.
4. Only then attempt per-row diagnosis of the 112 low / 30 high cells.

Everything the previous handoff said about the ~111 low cells still stands as an
open problem, but **do not start from its per-row leads** (Troponin ARIC, AHI
CHS) until row alignment is established. They may be artifacts.
